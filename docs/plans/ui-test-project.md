Java-адаптер записывает JSON и файлы вложений во время выполнения тестов. CLI отдельно читает эти результаты и генерирует HTML-сайт. Allure Java 3 официально совместим с Report 2 и Report 3; одинаковый major у этих компонентов не требуется. Официальные проверки адаптеров в релизе Java 3.0.0 использовали JUnit 6.1.0 и Selenide 7.17.0; наша точная комбинация 6.1.3 / 7.18.2 дополнительно проверена локальными прогонами этой фазы. Имеющийся JDK 21 подходит Gradle и адаптерам, которым требуется Java 17+.

`allure.properties` задаёт каталог результатов. `AllureJupiter` явно зарегистрирован на TestBase для отображения lifecycle fixtures; JUnit Platform listener поставляется адаптером через ServiceLoader. Для обычного запуска это обеспечивает `gradlew clean test`. ### Сохранение результатов и статус job

Сразу после тестового шага загружаются `allure-results` (`build/allure-results` целиком, со всеми вложениями) и `gradle-test-reports` (`build/test-results/test` и `build/reports/tests/test`). Каждый шаг проверяет наличие файлов и использует `!cancelled()`, поэтому выполняется после обычной ошибки предыдущего шага.

Затем генерация проверяет наличие `*-result.json`. Отсутствующий каталог, пустой каталог и только вложения без результатов вызывают явную ошибку «No Allure test results were produced; report was not generated», а не создание пустого успешного отчёта. Ненулевой exit code CLI сохраняется; после успешного CLI дополнительно проверяется `index.html`. Артефакт `allure-report` (`build/allure-report`) загружается только при успешном исходе генерации.

Сырые результаты загружаются до генерации, поэтому её ошибка не препятствует их сохранению. Ошибка одной загрузки не выключает остальные диагностические шаги с явными status conditions. В workflow нет `continue-on-error`, подавления exit code и автоматических ретраев тестов: упавший тестовый шаг оставляет job красным.

Контрольный вопрос: обычный следующий шаг имеет неявное условие `success()` и после падения пропускается. Явное `!cancelled()` снимает эту зависимость, но не меняет исход уже упавшего шага. Сохранение диагностики не равнозначно успешному выполнению тестов.

- `failure` + тестовый шаг `skipped` → ошибка подготовки, тесты не запускались.
- Ошибка тестового шага + проверенный XML с failures/errors → подтверждённое падение тестов.
- Ошибка тестового шага без надёжного XML → ошибка сборки/запуска, результат тестов отсутствует или не подтверждён; не «0 тестов».
- Ошибка тестового шага при корректном пустом XML → явно указаны ноль test cases, но это не успех запуска.
- Тестовый шаг успешен, итог job — `failure` → ошибка дальнейшей обработки CI (например, отчёт/артефакты), не падение тестов.
